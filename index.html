web-node

High level javaScript backend plugin system and configuration merger.

src.zip release en de fr API Documentation deDE: API-Dokumentation frFR: Documentation de l'API

Project Status

Use case

Assemble a Node.js backend from plugins. Each plugin is an npm package or a local folder that brings its own configuration and reacts to lifecycle hooks. web-node finds all plugins, merges their configurations into one, orders them by their dependencies, starts their services and shuts everything down cleanly. During development changed configurations and code can be reloaded without a restart.

Available plugins:

  • application-server: HTTP server for files and your own routes.
  • couchdb: CouchDB server with models, validation and authentication.
  • ejs: Renders EJS templates.
  • nginx: Runs nginx with a generated proxy configuration.
  • pre-render: Pre-renders pages of web applications.

Quick start

npm install web-node clientnode core-js

Your application is a plugin itself. Its configuration lives under the key "webNode" in its "package.json", its hooks are the functions exported by its "main" file:

{
  "name": "my-app",
  "type": "module",
  "main": "index.js",
  "webNode": {
    "myApp": {
      "greeting": "Hello"
    }
  }
}

// index.js
export const initialize = ({configuration, plugins}) => {
    console.log(configuration.myApp.greeting)
    console.log('Plugins:', plugins.map((plugin) => plugin.internalName))
}
export const exit = () => console.log('Bye')

Start it in the project folder:

npx web-node

Plugins

web-node loads these plugins:

  • Your application itself.
  • Every package in "node_modules" whose name ends with "web-node-plugin".
  • Every folder in "plugins" of your project.

A plugin is named in camel case without the suffix, e.g. "application-server-web-node-plugin" becomes "applicationServer". This name is its key in the shared configuration. Its configuration is read from the key "webNode" in "package.json" and an optional "private-package.json", e.g. for secrets not to be committed. Its hooks come from the file named in "main", otherwise from "index.js". If that file does not exist, another JavaScript or executable file is used, preferably one named "index" or "main":

{
  "name": "clock",
  "type": "module",
  "main": "index.js",
  "webNode": {
    "clock": {
      "interval": 1000,
      "ticks": 3
    }
  }
}

// plugins/clock/index.js
export const preLoadService = ({services}) => {
    services.clock = {count: 0}
}
export const loadService = ({configuration: {clock}, services}) => ({
    clock: new Promise((resolve) => {
        const timer = setInterval(() => {
            services.clock.count += 1
            if (services.clock.count >= clock.ticks) {
                clearInterval(timer)
                resolve()
            }
        }, clock.interval)
    })
})

A plugin which needs another one to be loaded before lists it in "dependencies", e.g. "webNode": {"myApp": {"dependencies": ["clock"]}}. "core.interDependencies" adds such relations from outside.

Plugins in other languages

If "main" points to an executable which is not a JavaScript file, it is run for every hook. It gets the hook name and further parameters (as JSON) as arguments and the hook data (as JSON) via standard input. It has to print a JSON object: "result" is its return value, a "status" of 404 marks a hook it does not implement and any other status from 400 on an error described in "message". Without such a status, "message" is logged as information. Further output for humans goes to standard error:

#!/usr/bin/env bash
# plugins/shell/api.sh with "main": "api.sh" in its "package.json"
case "$1" in
    initialize)
        echo '{"message": "Shell plugin initialized.", "result": null}'
        ;;
    *)
        echo '{"status": 404}'
        ;;
esac

Lifecycle

Each hook is called for every plugin in dependency order and gets a state object with "configuration", "plugins", "services", "servicePromises" and the plugin API "pluginAPI". Plugins which do not export a hook are skipped:

  1. "initialize": All plugins and their configurations are loaded.
  2. "preConfigurationLoaded" and "postConfigurationLoaded": Adjust the merged configuration.
  3. "preLoadService": Create service instances in "services".
  4. "loadService": Start services. Return an object mapping service names to promises which resolve when the service has finished. Before and after each plugin's call "preLoad<Name>Service" and "postLoad<Name>Service" run, e.g. "postLoadClockService".
  5. "postLoadService": All services are running.
  6. "shouldExit": All services have finished or "Ctrl+C" was pressed. Close connections here, asynchronous work is still possible.
  7. "exit": The process ends now, plugins are called in reverse order and only synchronous work is possible.

If a hook throws, "error" is called with the error in "data", followed by "shouldExit", and the process exits with code 1.

Plugins can define their own hooks. Call them for all plugins via "pluginAPI.callStack". It resolves to the value returned by the last plugin:

export const postLoadService = async (state) => {
    await state.pluginAPI.callStack({...state, hook: 'clockStarted'})
}

With TypeScript, "web-node/type" provides "PluginHandler" for the hook signatures and the state types.

Configuration

All plugin configurations are merged into one object in plugin order, so a plugin can change the configuration of the plugins it depends on, e.g. your application sets "applicationServer.port". Keys like "#" or "#1" are comments and removed. Values can be computed with "evaluate"; available are e.g. "currentPath", "path", "fs", "now" and "webNodePath":

{
  "webNode": {
    "applicationServer": {
      "#": "Listen on the host given by the environment.",
      "hostName": {
        "__evaluate__": "process.env.HOST_NAME ?? '127.0.0.1'"
      },
      "port": 8080
    }
  }
}

Command line arguments are merged last and win over all files:

npx web-node '{applicationServer: {port: 9000}, core: {debug: true}}'

The section "core" configures web-node itself:

  • "debug": Logs more and rethrows errors instead of only logging them.
  • "plugin.hotReloading": Reloads changed files, see below.
  • "plugin.directories": Where plugins are searched and which folder names count as plugins.
  • "plugin.configuration": File names and keys plugin configurations are read from.
  • "interDependencies": Additional dependencies between plugins.

Hot reloading

With "core.plugin.hotReloading" enabled, web-node checks before each hook call whether a plugin configuration or hook file has changed. Changed configurations are merged again between "preConfigurationHotLoaded" and "postConfigurationHotLoaded", changed hook files are imported again and announced via "apiFileReloaded":

npx web-node '{core: {plugin: {hotReloading: true}}}'

Own entry point

Instead of the "web-node" command you can start it from your own script and add plugins directly in code. Their "configurations" are shaped like a "package.json". "isMainModule" makes sure it only starts when the script is executed and not when it is imported:

// server.js
import {fileURLToPath} from 'node:url'
import main, {isMainModule} from 'web-node'

if (await isMainModule(fileURLToPath(import.meta.url)))
    await main({
        logger: {
            configurations: {webNode: {logger: {level: 'info'}}},
            scope: {
                initialize: ({configuration}) =>
                    console.log(configuration.logger.level)
            }
        }
    })
